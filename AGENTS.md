# Repository instructions for Codex and contributors

1. Before every task, read `docs/PRD/PRD.md`, `docs/REQUIREMENTS_TRACEABILITY.md` and `docs/PRE_CODE_READINESS_REPORT.md`; then read the affected rows in `docs/MASTER_PROMPT_COVERAGE.md` and `docs/ADDON_FEATURE_CATALOG.md` plus relevant architecture, milestone, risk, accepted ADR and normative specification.
2. Cite affected Requirement IDs in plans, changes, tests, commits and pull requests. Do not change/remove/weakening an ID without explicit owner approval and corresponding PRD/ADR/traceability updates.
3. Preserve module boundaries: domain/core must not import Bukkit/Paper/NMS, storage, Redis, proxy or provider implementations. Use public ports/adapters and no circular dependencies.
4. Never add TODO, FIXME, stub, placeholder implementation, fake/mock-only production behavior or claim completion without evidence. Do not silently reduce scope.
5. Do not block a Minecraft owner/tick thread with database, Redis, network, filesystem, compression or large calculations. Use bounded queues/executors, backpressure, timeouts and documented thread ownership.
6. Treat commands, permissions, GUI, API/events, PlaceholderAPI, configuration, localization, migration, performance, security, compatibility, tests and documentation as part of each feature—not follow-up work.
7. Use original or demonstrably licensed code/assets only. Do not package an asset or dependency without an approved exact provenance/licence row. Protect secrets and private moderation/replay data; sensitive actions require least privilege and audit.
8. Every change must leave a clean build and pass relevant unit, integration, regression, compatibility, migration, security and performance checks. Add regression coverage for bug fixes.
9. Update PRD/traceability, ADRs, risks, milestones, configuration/reference docs and release notes whenever the change affects them.
10. A feature is complete only when its PRD acceptance criteria and global Definition of Done are met. Report unresolved decisions or blocked criteria honestly.
11. Do not begin or expand Java implementation unless all three deterministic documentation validators succeed with the current `MASTER_PROMPT.md` hash, all 49 addon references/473 addon IDs, all 55 accepted decision IDs, all 199 Part I IDs and the 672-requirement/6,966-atomic-item totals; every row must be `COVERED` and overall coverage 100%. Regenerate/review reports after any source, catalogue, PRD or traceability change.
12. Before a build resolves any dependency, apply the exact selection and pre-resolution checksum/licence lock in `docs/DEPENDENCY_LICENSE_AUDIT.md`; never use a dynamic/range/floating SNAPSHOT release dependency. Never store or redistribute proprietary/provider/server binaries.
13. Follow the exact runtime/JDK/artifact matrix, benchmark and quality thresholds, network/scripting security controls, privacy/retention rules, operational RPO/RTO, clean-room/provenance policy and licensing gates. Deviations require an accepted ADR; difficulty is not authority to reduce scope.
14. A task is not complete until the clean build, applicable tests, deterministic validators and documentation/traceability updates all pass. Report external acquisition or release-evidence gates honestly; never call planned work implemented.
